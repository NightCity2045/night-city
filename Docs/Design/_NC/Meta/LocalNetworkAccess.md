# META: локальная сеть, сервер и доступ к двери

Статус: проект решений от 22 ноября 2026 года. Реализован только раздел 4 (дверь) и контракт раздела 7: компонент `NCMetaDoorAccess`, система `NCMetaDoorAccessSystem`, типы и события в каталоге API. Остальное (подключение устройств, резерв связи, сайт) ещё не написано. Имена в разделе 7 теперь реальные, а не предварительные. Нормативной остаётся `Specification.md`; при расхождении приоритет у неё, расхождение нужно устранить здесь.

Лор берётся из Cyberpunk RED только как фон. Правил настольного нетраннинга нет: нетраннер пишет код на META и действует против симулированной сети. Здесь описан первый слой этой сети: сервер, подключённые к нему устройства, сайт и дверь без ванильной системы доступа.

## 1. Принятые решения

| Тема | Решение |
| --- | --- |
| Доступ | Ванильная система доступов (ID-карты, `AccessReader`) для META-дверей не используется. Решение принимает программа META: на самой двери или на сервере. |
| Питание | На картах пока стоит `AlwaysPowered`. Связь между нагрузкой сервера и ваттами или теплом отложена. |
| Подключение устройства | Заявка на сервере, подтверждение на устройстве. Разрыв в обратном порядке: сначала сервер, потом устройство. |
| Ёмкость сервера | Резерв связи плюс трафик. Резерв считается один раз при создании и при смене маршрута. |
| Переполнение резерва | Новая связь отклоняется. Существующие связи не отбираются, сервер помечается как перегруженный. |
| Сервер недоступен | Дверь открывает любой. |
| Сервер подключён, но не ответил вовремя | Отказ и запись в журнал. |
| Сайт и посетители | Посетитель занимает сеанс и трафик, резерв связи не берёт. |
| Публикация сайта | Область задаётся для каждого вида: локальная сеть или CitiNet. Админская страница только локальная. |
| Админы | Список админов в файле сервера. Начальный админ — владелец сервера. |
| Идентификация | Персонаж кликает по двери. Сервер подставляет субъекта, сравнение по имени. Совпадающие имена получают одинаковый доступ, это принятый риск. |

## 2. Подключение устройств к серверу

Сейчас у устройства есть постоянный `DeviceId` (GUID), а в реестре `NCMetaDeviceRegistrySystem` есть эпохи `DeviceEpoch` и `AuthorityEpoch`. Рукопожатие строится на них.

1. На сервере владелец создаёт заявку: слот (например `main-door`), нужный интерфейс и код устройства.
2. Устройство показывает короткий код (6–8 символов, ограниченное время жизни). Полный GUID игрок не вводит.
3. Игрок рядом с устройством подтверждает заявку через меню. Проверяются владелец, дистанция, питание.
4. После подтверждения связь активна, эпоха повышается, резерв списывается атомарно.
5. Разрыв: сначала запись убирается на сервере, затем на устройстве. Резерв освобождается при удалении на сервере.
6. Принудительный сброс на устройстве нужен, если сервер потерян. Он стоит времени и инструмента и оставляет след (событие потери управления).

Условие: устройство, нарисованное в карте, без явного `deviceId` получает случайный GUID при каждом запуске (`Register`), и связь не переживёт перезапуск. Для дверей и серверов на карте идентификатор нужно задавать явно. Проверено по коду регистрации, восстановление после рестарта не проверялось.

### Как программа попадает на устройство

Код пишется только на терминале. У двери и у сервера редактора нет (`NCMetaTerminal.allowEditor: false`); у них остаётся «Панель META» (установка, восстановление, монитор оборудования, диагностика).

Два пути:
- **Чип в устройство.** Терминал экспортирует выпуск на носитель (`NCMetaProgramChip` или `NCMetaDataCartridge`, оба с тегом `NCMetaChip`). Носитель вставляется в слот `nc_meta_chip` двери. В «Панели META», вид «Установка», появляется кнопка «Загрузить программу с чипа»: программа попадает в рабочее пространство устройства и ставится обычным установщиком (связи, согласие, права). Чип остаётся физическим переносчиком; программа не зависит от того, вставлен ли он после установки.
- **Через сервер.** Программа стоит на сервере, дверь связана кабелем или радио. Сервер даёт мощность для сложной логики и сайтов.

Сильную защиту через чип не построить: профиль `NCMetaEmbedded` у двери ограничен (256 КиБ, один процесс, 4 единицы связи), поэтому чип подходит для простых правил, а серьёзная защита идёт через сервер.

Не сделано: режим «ПЗУ», когда программа работает только пока чип вставлен. Для него нужна связь установки с носителем в хранимых данных и отдельное подтверждение владельца двери.

### Кабель (решение, не реализовано)

Сейчас `NCMetaNetworkCable` — один предмет с двумя концами и проверкой длины: материал не тратится, на полу ничего нет. Принято положить кабель по тайлам и под плиткой, как провода.

- **Катушка** — стопка, каждая уложенная клетка тратит единицу. Укладка идёт через ванильный `CablePlacerComponent` без `overTile`: плитку надо вскрыть (подпол), как для низковольтных проводов.
- **Кусок кабеля** — закреплённая сущность на клетке с `SubFloorHide`, перерезается режущим инструментом (`CableComponent`, при перерезании выпадает единица катушки), может быть повреждён.
- **Связность** — собственный граф кусков (по соседям по сторонам), а не ванильные группы узлов. Так не нужен новый `NodeGroupID` и правка силовой визуализации. Визуальную маску соседей можно задавать через `WireVisVisuals.ConnectedMask`, клиентский визуализатор переиспользуется.
- **Подключение устройства**: порт на клетке с кабелем или на соседней по сторонам (для настенных панелей).
- **Расстояние** — длина маршрута в клетках. Она же идёт в резерв сервера, а `MaximumLength` как константа уходит.
- **Три уровня** — вертикальный переход отдельной деталью, отложено.
- **Переход**: старые кабели с двумя концами работают рядом, пока не перенесены сцены (`NCMetaDemoSceneSystem`) и тесты (`NCMetaPhysicalNetworkTest`).

Не проверено: как `CableSystem` режет произвольный `CableComponent` и нужно ли добавлять значение в `CableType` для запрета дублей на клетке (альтернатива — чёрный список по компоненту в `CablePlacer`).

## 3. Ёмкость сервера

Профиль оборудования получает число единиц связи (LU). Сервер крупнее, чем терминал или шлюз со встроенным хостом.

- **Резерв.** Каждая активная связь занимает часть LU. Кабель: небольшая базовая цена, расстояние почти не влияет, ограничение даёт длина кабеля. Радио: базовая цена выше плюс надбавка за тайлы, стены и помехи. Между уровнями отдельный множитель. Пересчёт идёт по `RoutingChanged`, а не каждый тик.
- **Трафик.** Уже есть: лимиты на порт, на владельца и общие, очереди по 16 сообщений и 32 KiB, нагрузка до 2048 байт плюс 128 служебных. Сейчас они глобальные. Нужна привязка к серверу и множитель расстояния для радио.
- **Переполнение.** Резерв проверяется только при создании связи. Если стену сломали и резерв стал больше ёмкости, связи остаются, сервер помечен `Overcommitted`, новые связи отклоняются.
- **Видимость.** Владелец видит таблицу связей: слот, устройство, среда, расстояние, резерв, трафик за минуту, состояние.
- **Числа.** Значения LU и множителей не выбраны, их нужно калибровать на сцене «шлюз и сервер» и на сцене в три уровня.

Три уровня: дистанция считается по `NCMapCoordinates` (сеть, позиция, `Z`). Существующая проверка радио `InRangeUnobstructed` про уровни ничего не знает, её поведение между этажами не проверялось.

## 4. Дверь: путь запроса

Все пути открытия двери (клик, столкновение, рука) проходят через `SharedDoorSystem.CanOpen`, который сначала поднимает отменяемое `BeforeDoorOpenedEvent`, а затем проверяет `HasAccess`. Это единственная точка перехвата.

Для META-управляемой двери:

1. Обработчик `BeforeDoorOpenedEvent` отменяет ванильное открытие, если нет одноразового разрешения для пары «дверь, пользователь».
2. Сервер определяет состояние связи в момент клика:
   - связи нет или процесс не запущен: исход `Unavailable`, дверь открывается для всех;
   - иначе: поднимается событие `accessRequested` с субъектом.
3. Программа отвечает методом `answerAccess(requestId, allow)`. Ответ `allow` выдаёт одноразовое разрешение и вызывает открытие. Ответ `deny` проигрывает отказ (`Deny`).
4. Нет ответа за срок (сейчас жёстко 2 секунды в `NCMetaDoorPanelSystem`, нужен параметр двери): исход `TimedOut`, дверь не открывается, запись в журнал.
5. У двери не должно быть `AccessReader`: `HasAccess` без него возвращает `true`, и после разрешения открытие не блокируется. Прототип `Airlock` (родитель `NCMetaDoor`) содержит `AccessReader` с `containerAccessProvider: board` и платой `DoorElectronics`, поэтому для META-дверей этот компонент нужно убрать в прототипе `NCMetaDoor`.

Ошибка текущего поведения: при молчании программы панель через 2 секунды открывает дверь запасным путём. Отказ программы, выраженный отсутствием `setOpen`, превращается в разрешение. Явный `deny` и состояние `TimedOut` это исправляют.

Столкновение: открывается по тому же пути и создаёт тот же запрос. Повторные запросы от одного пользователя к одной двери склеиваются (в панели это уже есть: `_pending` по ключу «дверь, пользователь, открыть») и ограничиваются по частоте.

Журнал: на двери хранится небольшой кольцевой буфер исходов (`Allowed`, `Denied`, `TimedOut`, `Unavailable`) с временем, именем и номером запроса. Программа получает событие `accessResolved`, если она жива.

Предположение, которое не проверено: клиент предсказывает открытие двери по клику (`predicted: true`). Чтобы не было ложного открытия на клиенте, обработчик для управляемой двери должен быть общим (shared) и отменять открытие на клиенте всегда.

## 5. Идентификация

Субъект подставляет сервер из персонажа у двери. Программа создать его не может: нативные DTO не конструируются (`new` разрешён только для пользовательских структур).

- Поля: имя для показа и ключ на базе `NCCharacterId`.
- Сейчас сравнение только по имени. Ключ в типе остаётся на будущее, использовать его не обязательно.
- Позже добавляется носитель (пропуск с `NCItemId`). Тип расширяется отдельным полем, существующие программы не ломаются.
- Список доступа хранится в файле сервера (`FileStore`, атомарная запись) и редактируется формой MUI.

## 6. Сайт на сервере

- **Область публикации** для каждого вида (view): локальная сеть или CitiNet. В контракте MUI виды уже адресуются отдельно.
- **Локально:** без домена, платы и срока. Видна устройствам, достижимым по физической сети сервера. Сеансы ограничены небольшим фиксированным числом и расходуют память и gas процесса.
- **CitiNet:** действующая модель аренды (`DomainFee`, `HostingUnitFee`, `TermSeconds`, `CapacityUnits`, `SessionsPerUnit`, грация). Нужен рабочий шлюз (в порту есть `GatewayNetworks`).
- **Админская страница** только локальная.
- **Права на правку** списка доступа определяет список админов. Один тип субъекта используется и для двери, и для веб-сеанса.
- **Начальный админ** — владелец сервера. Владелец может сбросить список физически.

### Компьютер-обозреватель

Отдельный терминал, на котором открываются локальная сеть и CitiNet. Список локальных сайтов он собирает при открытии, запросом к серверам, достижимым по сети (с кешем и ограничением числа результатов). Для просмотра терминалу не нужна связь с резервом: он клиент, занимает сеанс и платит трафиком. Скрытые сайты (без объявления в списке) доступны по точному имени.

## 7. Черновик контракта

Названия предварительные. Старое событие `DoorRequest` не меняется: оно входит в версионируемый каталог API, на нём завязаны шаблоны и тесты.

| Что | Описание |
| --- | --- |
| `meta.access.Subject` | Нативный DTO: `name:string`, `key:string`. Только для чтения, не конструируется программой. |
| `meta.doors.AccessOutcome` | Перечисление: `Allowed`, `Denied`, `TimedOut`, `Unavailable`. |
| `meta.doors.AccessRequest` | DTO: `requestId:string`, `subject:Subject`, `open:bool`, `stamp:SampleStamp`. |
| `meta.doors.Door.accessRequested` | Событие `Ordered`, очередь 16, источник сама дверь. |
| `meta.doors.Door.answerAccess(requestId, allow)` | Асинхронный метод, возвращает `result<DoorState>`. Эффект: одноразовое разрешение и открытие, либо отказ. |
| `meta.doors.Door.accessResolved` | Событие с `requestId`, субъектом и `AccessOutcome`. |

Изменения кода (оценка, не реализация): общий компонент и система для управляемой двери (обработчик `BeforeDoorOpenedEvent`, одноразовые разрешения, журнал); серверный мост к каталогу API и рантайму; запись в каталоге API с фикстурами и проверками совместимости; снятие `AccessReader` у META-дверей в прототипах и на картах.

## 8. Что проверено в коде, а что нет

Проверено чтением:
- `TryRequest` панели проверяет ванильный `HasAccess` до отправки события в META.
- `DoorRequest` содержит только `open`, `requestId`, `stamp`.
- Профили оборудования, порты, кабели, радио, лимиты трафика и профиль хостинга существуют, как описано выше.
- `CanOpen` вызывает `BeforeDoorOpenedEvent` до `HasAccess`.
- `NCMetaDoor` наследует `Airlock`, а у `Airlock` есть `AccessReader` (плата `DoorElectronics`).

Не проверено:
- Какие двери на картах используют `NCMetaDoor`, а какие остаются обычными `Airlock`.
- Поведение радио между уровнями и работа `NCZGrid` для связи.
- Уникальность имён персонажей (решено не требовать).
- Восстановление связей после рестарта и стабильность `DeviceId` у устройств на картах.
- Предсказание открытия двери на клиенте.
